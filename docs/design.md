# 设计说明：把同步服务拆成低权限主进程 + 高权限助手

面向读者：维护这个服务的工程师，以及要评审这次拆分的安全同学。
代码在哪里：`crates/`。怎么跑：见 [README](../README.md)。

---

## 1. 问题

原服务是一个进程，以 root 常驻。它做两类事：

* **需要特权的**：挂载/卸载磁盘、改几项系统设置。两三件事。
* **不需要特权的**：解析网络数据、校验路径、拷贝文件、冲突处理。代码量大，
  输入完全由外部控制。

两者在同一地址空间、同一权限下。任何一处解析漏洞——一个越界读、一个
`../` 没拦住、一个整数溢出——直接就是 root。所以真正的目标不是"把代码
写得更安全"，而是**让解析代码根本不持有特权**：即使它被完全攻破，损失也
只是普通用户的权限。

## 2. 拆分后的两块

| | 主进程 `syncd-agent` | 助手 `syncd-helper` |
|---|---|---|
| 权限 | 登录用户（uids 与用户相同） | root（真实部署） / `--simulate`（演示） |
| 代码量 | 大：网络、路径、文件、冲突处理 | 小：四件事 + 鉴权 + 策略 |
| 输入 | 不可信网络数据 | 只读 64 字节定长帧 |
| 被攻破后 | 用户权限 | 只能做四件事 |

关键点：**两边的解析语义是同一份代码**（`crates/sync-core`，经
`PrivOps` trait 抽象）。拆分改变的不是行为，而是这段代码运行时的权限。
因此"拆分前后对比"是干净的对照实验，不是两个不同的程序。

## 3. 接口为什么划成这样

接口是 `crates/protocol`（`sync-wire`），一条 Unix socket。设计取舍：

### 3.1 定长帧，没有长度字段

请求恰好 **64 字节**，回复恰好 **32 字节**。没有变长字段，于是：

* 接收路径上没有分配器，没有"先读长度再分配"这类经典漏洞面；
* 攻击者无法让助手把任意多的数据回传（文件、内存、密钥）。32 字节就是上限。

### 3.2 没有字符串、没有路径、没有命令

请求里只有一个小的操作枚举和定宽标识符。**磁盘用 UUID 命名，助手自己把
UUID 映射到路径**，这个表来自 root 拥有的文件。所以主进程即使被完全控制，
也无法（a）指定一个路径，（b）指定一条命令，（c）设置环境变量。

这是整个设计的核心决定。一个"传路径给助手挂载"的接口会把所有路径校验
成本推回助手，而助手恰恰应该是那个没有复杂解析逻辑的进程。UUID 把"命名
对象"和"授权对象"分开了：主进程只能**指认**，不能**定义**。

### 3.3 闭合的操作集合，未使用位必须为零

`Op` 四个值，`SettingId` 三个值，其它字节一律拒绝；参数区未使用的字节必须
为零。解析是**全函数**：任何输入都得到 `Ok` 或一个具体的错误，不会 panic
（`crates/protocol/src/lib.rs` 里有逐字节变异的穷举测试）。

推论：**不存在任何字节串能解码成"执行命令"**。这是协议层的性质，不依赖
助手写得对。

### 3.4 一连接一请求

助手对每个连接只读一帧、回一帧、关闭。没有跨请求的连接状态可以被污染，
也就没有状态机可以被打乱。

### 3.5 序号严格递增

每帧带 `seq`，助手按对端审计令牌记录已见过的最大值，回退或重放一律拒绝。
这让"录下合法帧再重放"即使对合法对端也无用。

## 4. 助手如何校验来源

这是最容易写错的一环，所以先给实测结论（macOS 26.5，arm64）。

### 4.1 两个容易被忽略的事实

**事实一：审计令牌跨 `exec` 存活，但它指向的镜像是当前的。**
实测：一个进程连上助手后 `exec` 成 `/bin/sh`，同一连接的审计令牌解析出来
的代码哈希是 `sh` 的，不是原来那个进程的。所以在 `accept()` 时校验一次
是**错的**——它授权的是发起连接的镜像，而发帧的是另一个镜像。

**事实二：socket 可以用 `SCM_RIGHTS` 交给别的进程。**
实测：`LOCAL_PEERPID` 会跟着变成**接收方**进程的 pid，审计令牌也一样。
所以按 pid 授权同样不够。

结论：**来源校验必须在读到帧之后、每一帧都做**，并且解析的是"此刻"的镜像。
助手就是这么写的（`crates/helper/src/server.rs`，步骤 2）。

### 4.2 校验的是"哪个程序"，不是"能做什么"

助手做的事：从 socket 取 32 字节审计令牌 → `SecCodeCopyGuestWithAttributes`
→ `SecCodeCheckValidity` 对着 `cdhash H"<白名单>"` 要求求值。`SecCodeCheckValidity`
同时校验签名本身，所以一个被篡改、只是"看起来像"白名单镜像的程序过不了。

它**不**做的事：限制一个白名单程序能请求什么。一个被完全控制的主进程仍然
是**真正的主进程**，哈希也对。挡住它的是协议和助手自己的策略（第 3、5 节）。
两道机制缺一不可：

* 代码签名白名单：挡住**不相干的**本地进程（比如攻击者丢进来的一个二进制）；
* 协议 + 策略：即使**合法**主进程被完全控制，也只能请求四件事。

### 4.3 pid 不参与授权

`LOCAL_PEERPID` 只用于日志。pid 会被回收，按 pid 授权会引入一个可被利用的
窗口。代码里也没有"令牌解析失败就退回 pid"的分支——解析失败就是拒绝
（fail closed），这在第 5.3 节会说明代价。

### 4.4 一个真实测到的边界情况

exec 之后**立刻**解析令牌，`SecCodeCopyGuestWithAttributes` 可能返回
`-67065`（镜像尚未完全就绪）。集成测试
`exec_to_unlisted_image_is_refused` 覆盖了这条路径：它的断言是"第二帧
**没有**被接受"，而不是"必须返回某个特定错误码"。两种情况（解析成功但
哈希不匹配 / 解析失败）都是拒绝，安全结论相同。

这意味着：如果主进程在发请求的那一刻恰好正在 exec，助手会拒绝这次请求而
不是接受。代价是偶发失败，收益是绝不放行一个没校验过的镜像。**这个取舍
是刻意的**，见 5.3。

## 5. 助手自己的策略（第二道墙）

身份校验之后，助手**不信任**请求里的任何东西，只用自己的状态裁决：

* 从 root 拥有的表文件读白名单（`--table`；非 root 拥有则拒绝启动，
  `--simulate` 除外）；
* UUID 必须在表里，且该条目必须标了 `allow_mount=1`。未知 UUID 和"已知但
  不可挂载"返回**不同的** detail 码，便于排查；
* 设置只有三个、取值只有 0/1，协议层和策略层各查一次（纵深防御）。

表文件里的挂载点来自**助手自己**，请求里没有路径。所以"挂载任意路径"这个
滥用在新架构里连表达都表达不出来。

### 5.1 为什么设置不能写成"改任意设置"

保留三个具体设置，而不是一个 `Set(key, value)`。因为一旦引入 key 字符串，
就把"解释攻击者提供的标识符"这件事又放回了助手——正是要避免的。新增设置
需要改代码、重新评审、重新签名，这是**特性**不是缺陷。

### 5.2 一处诚实的边界

助手策略允许"卸载一个在白名单里、且标了可挂载的卷"。这是产品本来就授予的
能力，不是漏洞。攻击矩阵里这一行标为 `YES` 并注明原因，没有硬凑成全 `no`。

### 5.3 失败关闭，而不是失败放行

助手在以下情况一律拒绝：取不到审计令牌、令牌长度不是 32、镜像解析失败、
哈希不在白名单、uid 不在白名单（若启用）、表文件不是 root 拥有、白名单为空。
其中"白名单为空拒绝启动"和"表文件必须 root 拥有"在
`crates/helper/src/main.rs` 与集成测试 `helper_refuses_to_start_without_allow_list`
里都有覆盖。

## 6. 拆分前 / 后：可被滥用的操作对比

下表由 `cargo run -p syncd-redteam --bin redteam` 打印，同样的数据被
`crates/redteam/src/lib.rs` 的单元测试断言。前提都一样：**攻击者已经完全
控制了那条"解析不可信输入的代码路径"**。

| 滥用 | 拆分前（单进程 root） | 拆分后（主进程被控） |
|---|---|---|
| 挂载任意路径 | **能**：`mount_volume("/etc")` 直接返回成功 | **不能**：请求里只能放 UUID，策略拒绝表外 UUID |
| 改任意系统设置 | **能**：直接写进程内状态 / 调系统 API | **不能**：只有三项设置、取值 0/1 |
| 以 root 读写任意文件 | **能**：`/etc/sudoers`、`authorized_keys` 都可写 | **不能**：协议里没有文件操作；主进程自己的文件代码是用户权限 |
| 以 root 执行任意程序 | **能**：`Command::new` 继承 euid 0 | **不能**：没有 exec 操作，助手从不 fork |
| 安装持久化 | **能**：写 `LaunchDaemons` 并加载 | **不能**：用户权限没有写权限，协议也没有对应操作 |
| 读取内存里的密钥 | **能**：同一地址空间 | **不能**：不同进程，只交换两个定长帧 |
| 卸载白名单内的可挂载卷 | **能**（本就是产品能力） | **能**（本就是产品能力） |

单进程版 7/7 可行；拆分版 1/7，且那 1 项是产品本来就要授予的能力。

## 7. 这个设计**没有**解决的问题（务必读）

诚实的边界比漂亮的结论更有用。以下是仍然存在、且需要在真实部署里另行处理
的问题：

1. **演示中的特权操作是模拟的。** `mount_volume` 在 `--simulate` 或普通
   用户下只检查路径是否为绝对路径。真实部署要把它们接到 `diskutil`，并在
   发布签名里授予 `com.apple.private.diskutil` 之类的权利。这一步的代码不
   在演示里。

2. **助手只做了代码哈希白名单，没有做 designated requirement 校验的强制
   链。** 生产环境应该用 `identifier "..." and anchor apple generic and
   certificate leaf[subject.OU] = "<TeamID>"` 这类要求，而不是裸哈希。裸
   哈希的问题：同一二进制被换过的副本、或者哈希被预置进表，都会绕过。
   代码里 `AuthPolicy` 已经把"归一化 + 解析"集中到一处，替换成要求串是
   局部改动。

3. **socket 的目录权限是信任根。** 助手会收紧 socket 为 `0660`，但如果
   `/var/run` 可被非 root 写，攻击者能替换 socket 诱导主进程连到假的助手
   （那是降级，不是提权：假助手没有 root）。真实部署应把 socket 放在
   root 拥有、非全局可写的目录里，并用 `launchd` 的 `Sockets` 键管理。
   代码里 `HelperServer::restrict_permissions` 是第二层，不是唯一一层。

4. **助手不限制连接频率 / 并发。** 一个被控制的主进程可以疯狂重连。代码里
   留了 `serve` 循环，没有限流。生产环境应在 launchd 或代码里加连接速率
   限制，防止 CPU 耗尽（这是 DoS，不是提权）。

5. **重放防护是每进程内存状态，重启即清空。** 一个跨重启的录制-重放窗口
   存在。缓解：重放一帧"挂载一个已挂载的卷"本身没有新增危害，而序号由主
   进程自己的计数器保证不重复。若要更严格，可在助手侧持久化每个令牌的
   最大序号——但那会把状态和隐私问题引进来，演示里没做。

6. **`LOCAL_PEERPID` 与令牌解析的竞态。** 助手在"读帧之后"解析令牌，此时
   对端可能已经再次 exec。这不会导致放行错误镜像（解析的是当前镜像），但
   会导致偶发拒绝（见 4.4）。若要把误拒降到最低，可以在一帧内重试解析
   若干次，演示里没做。

7. **审计令牌长度断言是 macOS 特定的。** 代码假定 `LOCAL_PEERTOKEN` 返回
   32 字节；非 32 字节一律拒绝。这在 macOS 上是正确的，换平台需要重写
   `auth.rs`（Linux 上对应 `SO_PEERCRED` / `SO_PEERSEC`，语义不同）。

8. **演示用 TCP 做前端。** 主进程监听 `127.0.0.1`，没有 TLS、没有认证。
   真实服务的网络层不在这次拆分的范围内；拆分只保证"网络层被攻破"的损失
   被限制在用户权限。

## 8. 如何验证这些声明

```bash
cargo test --workspace          # 48 个单元测试，含协议逐字节变异与 50 万随机帧的穷举测试
./scripts/test-integration.sh   # 6 个集成测试，跑真实助手进程
./scripts/demo.sh               # 拆分前后并排演示 + 攻击矩阵
```

集成测试里最有价值的三个：

* `unlisted_caller_gets_uniform_refusal`：不在白名单的调用者，无论发什么帧
  形状都得到同一个拒绝——说明策略根本不会被无权限调用者触达。
* `exec_to_unlisted_image_is_refused`：合法调用者 exec 成 `/bin/sh` 后发帧，
  助手拒绝。**这是"每帧校验当前镜像"的核心证据**，并且探针会先证明那一帧
  确实送到了 socket，避免测试假通过。
* `authorised_caller_cannot_replay`：合法调用者重放同一 `seq`，第二次被拒。
